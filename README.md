# jev-insight-app

展示会ブースで、担当者と来場者の会話をスマホで録音し、来場者の会社・団体が抱える「課題」を見つけるための Web アプリです。
会話の文字起こしを [TypeSafe AI](https://typesafe.ai/) の **Jev** で発話ごとに判定し、課題に関係する発言だけを残します。会話の終了時には、ローカルの LLM が来場者向けのまとめと、ブース担当者向けのリードデータを作ります。

## 主な機能

- **来場者の登録**: 来場者証の QR コードをスマホのカメラで読み取ります。読み取った内容は URL 全体をそのまま保存します。QR があれば、会社名・氏名は省略できます。
- **録音と判定**: 8 秒ごとに音声を送り、文字起こしをすぐ画面に表示します。Jev の判定が終わると、課題カードか「破棄」に切り替わります。
  - 次の発言は保存しません: あいさつ・雑談、出展者側の質問、画面の質問を読み上げた声、短すぎる断片
  - 課題カードには、Jev の課題スコア（0〜1）と深刻度（1〜5）を数値で表示します
- **深掘りの支援**: まだ聞けていない情報（規模・予算・時期・決裁者など）を Jev が選び、「次に聞いてみる」質問として表示します。あわせて「課題の具体度」（0〜3）をメーターで表示します。
- **来場者向けのまとめ**: 会話を終了すると、次の内容を来場者本人に見せます。
  - 本人が言葉にしていなかった「背景にある課題」
  - お話のテーマの比重
  - おすすめの業務改善と、その最初の一歩
- **担当者向けのリード**: 商談見込み（A/B/C）、次のアクション、アポイント依頼文を保存します。一覧からリードページを開くか、CSV で出力して確認します。
- **来場者アンケート**: 来場者が自分のスマホで開き、来場者証の QR を読み取ってから設問に答えます。回答すると「コーヒー引換チケット」が表示されます。
  - 展示会は複数日あるので、アンケートとチケットは来場者証 1 枚につき 1 日 1 回です。2 日目に来た方も、同じ来場者証でもう一度答えると新しいチケットが出ます。日付は日本時間で区切ります。
  - 同じ日に同じ QR で答え直しても、その日の最初の回答と同じチケットが出ます。その日に回答済みの来場者証の QR を読むと、設問を出さずにチケットの画面へ進みます。
  - チケットには「10/28（水） 当日限り」のように日付が出ます。前の日の使っていないチケットは「期限切れ」になり、お渡し済みにできません（その日のアンケートへの案内が出ます）。
  - チケットを開いた端末では、ページを閉じても `/survey` の丸ボタンが「コーヒー引換チケットを表示する」に変わります。お渡し済みになるか、日付が変わると元に戻ります。
  - 社内テストでは `SURVEY_ALLOW_REANSWER=1` にすると、同じ QR で答え直せます。Docker で動かしている場合は `.env` に書いて `docker-compose up -d` で反映します（再ビルドは不要です）。オンの間は「アンケート回答」画面に表示が出ます。
  - コーヒーを渡すときに、担当者が来場者の画面のボタンを長押しして「お渡し済み」にします。
  - アンケートの入口の QR は、担当者用の「課題メモ」「アンケート回答」のどちらの画面からも、「アンケートのQRを表示」で出せます。開いているホストの `/survey` を指すので、公開用の URL で開いた端末で表示してください。
  - 設問は `lib/survey.ts` にあります（いまはサンプルです）。
  - 回答は担当者用の一覧と CSV で確認できます。同じ QR の課題メモがあれば、相互にたどれます。

## 構成

```
スマホ（ブラウザ）
   │ 8秒ごとの音声（webm / mp4）
   ▼
Next.js（App Router, Node.js）
   ├─ whisper.cpp（whisper-server）      文字起こし
   ├─ TypeSafe AI Jev（System One API）   発話の判定・深掘り質問・商談見込み
   ├─ gemma-4-12b（llama-server）        終了時のまとめ（来場者向け／担当者向けを並列で作成）
   └─ SQLite（Drizzle ORM）              data/insight.db
```

Jev は文章を生成せず、`noul`（はい／いいえの確率）・`choice`（選択肢）・`score`（段階評価）を返します。
そのため、課題の抽出は「発話ごとに判定し、関係するものだけを残す」方式にしています。文章の生成は gemma が担当します。

| 使っているところ | Jev への質問 |
|---|---|
| 発話ごと | 課題に関係あるか / 来場者自身の話か / テーマ / 情報の種類 / 深刻度 / 予算・時期・決裁者への言及 |
| 会話中 | 次に確認すべき不足情報 / 商談見込み（課題の具体度） |
| 終了時 | 商談見込み（A/B/C の判定） |

質問の定義は `lib/jev-questions.ts` にあります。

## 必要なもの

- Node.js 22 以降
- [whisper.cpp](https://github.com/ggml-org/whisper.cpp) の `whisper-server` と、日本語に対応したモデル（`ggml-large-v3-turbo` を推奨）
- ffmpeg（whisper-server の `--convert` オプションで使います）
- OpenAI 互換 API で使える LLM サーバ（[llama.cpp](https://github.com/ggml-org/llama.cpp) の `llama-server` で gemma-4-12b を動かすことを想定しています）
- TypeSafe AI の API キー

## セットアップ

```bash
npm install
cp .env.local.example .env.local   # TYPESAFE_API_KEY を設定する
```

| 環境変数 | 既定値 | 説明 |
|---|---|---|
| `TYPESAFE_API_KEY` | （必須） | TypeSafe AI の API キー |
| `TYPESAFE_MODEL` | `jev-latest` | Jev のモデル名 |
| `WHISPER_URL` | `http://127.0.0.1:8090` | whisper-server の URL |
| `GEMMA_URL` | `http://127.0.0.1:8080` | llama-server の URL |
| `RELEVANCE_THRESHOLD` | `0.5` | この値以上の発言だけを課題として保存します |
| `DATABASE_PATH` | `./data/insight.db` | SQLite のファイルの場所 |
| `CF_ACCESS_TEAM_DOMAIN` | （なし） | Cloudflare Access のチームのドメイン（`<チーム名>.cloudflareaccess.com`）。下の「スマホから使う」を参照 |
| `CF_ACCESS_AUD` | （なし） | 担当者用の画面を守っている Access アプリの AUD タグ |
| `SURVEY_ALLOW_REANSWER` | （なし） | 社内テスト用。`1` にすると、同じ来場者証で何度でもアンケートに答え直せます（その日の前の回答とチケットは消えます）。当日は設定しないでください |

whisper-server と llama-server を起動します。

```bash
whisper-server -m ~/.local/share/whisper-models/ggml-large-v3-turbo-q5_0.bin \
  --host 127.0.0.1 --port 8090 -l ja --convert

llama-server -m gemma-4-12b-it-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8080 -c 131072 --parallel 12 --kv-unified
```

- 会話を終えると、担当者向けと来場者向けのまとめを同時に作ります。複数のブースで同時に使うときは「ブースの数 × 2」の枠を `--parallel` で用意します（上の例は 6 ブース分）。`--kv-unified` を付けると、枠を増やしても 1 件あたりに使える文脈の長さが減りません。
- アプリ側から thinking を無効にして呼び出します（有効だと 1 分近くかかるためです）。

## 起動

```bash
npm run dev            # 開発（http://localhost:3000）
npm run build && npm start   # 本番（ポート 3200）
```

DB のマイグレーションは、アプリが最初に DB を開いたときに自動で適用されます。
スキーマ（`lib/db/schema.ts`）を変えたら `npm run db:generate` でマイグレーションを作り、サーバを再起動してください。

### スマホから使う

マイクとカメラは HTTPS でないと使えません。スマホから使うときは、Cloudflare Tunnel などで HTTPS の URL を用意してください。
アプリ自体にはログイン機能がありません。公開する場合は、Cloudflare Access などで前段に認証を置いてください。

来場者アンケートだけは、認証なしで開けるようにします。前段で認証を外してよいパスは次の 6 つです。

- `/survey`
- `/survey/*`
- `/_next/static/*`
- `/favicon.ico`
- `/manifest.webmanifest`
- `/icons/*`

最後の 2 つはホーム画面に追加する（PWA）ためのものです。ブラウザはマニフェストとアイコンを Cookie なしで取りに行くので、認証の内側に置くとログイン画面に飛ばされ、アプリとして追加できません。中身はアプリ名とアイコンだけです。

それ以外（`/`、`/responses`、`/sessions/*`、`/leads/*`、`/api/*`）は、必ず認証の内側に置いてください。`/survey*` のような前方一致で書くと範囲が広がるので、上のとおりに指定します。

公開ページを足すときの注意:

- 担当者だけが使う操作は、Server Action ではなく Route Handler（`/api/...`）で作ります。Server Action は、公開しているページへの POST からも呼び出せるためです。
- 既存の `createSession`（課題メモの新規作成）は Server Action のままなので、最初に `isStaffRequest()`（`lib/access.ts`）で、Access を通ったリクエストかを確かめています。Access がログイン済みのリクエストに付ける署名付きのトークン（`Cf-Access-Jwt-Assertion`）を、`CF_ACCESS_TEAM_DOMAIN` と `CF_ACCESS_AUD` で検証します。担当者用の Server Action を足すときも、同じように最初に呼んでください。
  - 2 つの値は、ログイン画面の URL から分かります。ドメインは `https://<チーム名>.cloudflareaccess.com/...` の部分、AUD タグは `kid=` の値です。ダッシュボードでは、Access のアプリの設定にある「アプリケーション Audience (AUD) タグ」です。
  - 本番（`NODE_ENV=production`）で 2 つの値が無いときは、課題メモを作れません。手元の開発（`npm run dev`）では確かめずに通します。
- アンケートの操作（QR の確認・回答・お渡し済みにする）は、同じ IP アドレスから 10 秒に 30 回までにしています（`lib/rate-limit.ts`）。超えると「混み合っています」と出ます。
  - IP アドレスは Cloudflare が付ける `CF-Connecting-IP` で見ます。会場の Wi-Fi や携帯の回線では大勢が同じ IP アドレスに見えるので、人には届かず、スクリプトだけが超える回数にしています。
  - 新しいチケットの発行は止めません。同じ IP アドレスから 10 分に 30 枚を超えると、ログに `[survey]` で始まる警告を出します（`docker logs jev-insight-app` で見られます）。
  - 数はメモリに置いているので、コンテナを入れ替えると数え直しになります。
- 来場者証の QR の形式は確かめていません。どんな QR でもチケットが出るので、コーヒーを渡すときに実物の来場者証を確認してください。

## ロゴ

来場者アンケートとチケットには、ブースの「OCCカフェ」のロゴを出します。ロゴは商標を含むので、このリポジトリには入れていません。
ビルドする前に、背景が透明な SVG（正方形）を `public/survey/occ-cafe-logo.svg` に置いてください（`.gitignore` 済み）。
置かずにビルドすると、ロゴの場所には代わりの文字「OCCカフェ」が出ます。

URL は `/survey/occ-cafe-logo.svg` になるので、前段の認証から外すパス（`/survey/*`）に含まれます。

## 画面

| パス | 対象 | 内容 |
|---|---|---|
| `/` | 担当者 | 課題メモの一覧（商談見込み順・テーマで絞り込み）、CSV 出力 |
| `/sessions/new` | 担当者 | 来場者の登録（QR 読み取り） |
| `/sessions/[id]` | 担当者 → 来場者 | 会話中は録音画面、終了後は来場者向けのまとめ |
| `/leads/[id]` | 担当者 | リードの詳細（商談見込み・次のアクション・抜き出した発言） |
| `/api/export` | 担当者 | リードの CSV（Excel で開ける UTF-8 BOM 付き） |
| `/responses` | 担当者 | アンケート回答の一覧（お渡し済みの件数、回答の内容、課題メモへのリンク）、アンケート入口の QR 表示 |
| `/api/export/survey` | 担当者 | アンケート回答の CSV |
| `/metrics` | 担当者 | 負荷の記録（1 分ごとのアクセス数と処理時間）。アンケート回答の画面の「負荷の記録」から開く |
| `/api/export/metrics` | 担当者 | 負荷の記録の CSV |
| `/survey` | 来場者（公開） | アンケート（QR 読み取り → 設問） |
| `/survey/ticket/[token]` | 来場者（公開） | コーヒー引換チケット |

## 当日の負荷

当日にアクセスがどれだけ集中したかを、あとから見られるように記録します。

- **アプリの中の記録**（`lib/metrics.ts`）: 1 分ごと・種類ごとに、リクエストの件数（`proxy.ts` で数える）と、文字起こし・Jev・gemma・アンケートの操作にかかった時間、同時に動いていた数の最大を DB の `metrics` に残します。IP アドレスや回答の中身は残しません。`/metrics` で見られ、CSV にも出せます。
- **Mac の負荷**: 当日はサーバの Mac で `scripts/monitor.sh` を動かしておきます。15 秒ごとに load average・GPU 使用率・メモリの空き・アプリのコンテナ・whisper-server・llama-server の CPU とメモリを `data/monitor-<日付>.csv` に書きます。

  ```bash
  nohup scripts/monitor.sh > /dev/null 2>&1 &   # 止めるときは pkill -f scripts/monitor.sh
  ```

- **負荷試験**（`scripts/loadtest.mjs`）: 当日の前に、手元で動かしたサーバ（DB はコピー）や whisper-server・llama-server に直接送って測ります。使い方はファイルの先頭にあります。Jev は外部の API なので、負荷試験では呼びません。

## プライバシー

- 録音を始める前に、来場者の同意を確認するチェックがあります。
- 音声ファイルは保存しません。
- 文字起こしのうち、Jev が課題に関係ないと判定した発言も保存しません。
- アンケートは、回答の利用に同意するチェックを入れないと送信できません。
- チケットの画面には、氏名や回答を表示しません（URL を知っていれば開けるためです）。
